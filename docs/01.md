## 1. What this project actually is

We're building an **AI customer-support agent**, not just a chatbot.

The final architecture is roughly:

```text
                         CUSTOMER
                            │
                            ▼
                 Amazon Bedrock AgentCore
                      Runtime
                            │
                            ▼
                     Strands Agent
                       (main.py)
                            │
        ┌───────────────────┼─────────────────────┐
        │                   │                     │
        ▼                   ▼                     ▼
 AgentCore Gateway    Knowledge Base         AgentCore Memory
        │                   │                     │
        │              Product/policy         Customer facts
        │              information            & preferences
        │
   ┌────┴─────────────┐
   │                  │
   ▼                  ▼
Order API        Refund Lambda
   │
API Gateway
   │
order-tracker
Lambda


Additional Agent Tools
        │
        ├── Code Interpreter → loyalty calculations
        │
        └── Browser → live web browsing
```

The final agent therefore has **six major capabilities** required by the project: order tracking, refunds, RAG/product-policy questions, cross-session memory, loyalty calculations, and browser access.

# 4. Lambda execution role

Then we created:

```text
CustomerSupportLambdaRole
```

Why?

AWS Lambda shouldn't simply have unrestricted access to your AWS account. A Lambda runs using an **IAM role**.

We created this trust relationship:

```text
AWS Lambda
    │
    │ assumes
    ▼
CustomerSupportLambdaRole
```

The trust policy allows:

```text
lambda.amazonaws.com
```

to assume the role.

Then we attached:

```text
AWSLambdaBasicExecutionRole
```

That gives the Lambda basic CloudWatch logging capabilities.

So:

```text
CustomerSupportLambdaRole
│
├── Trusts Lambda
│
└── Can write Lambda execution logs
```

```text
GET /orders/{order_id}

GET /customers/{customer_id}

GET /customers/{customer_id}/orders
```

These are exactly the order API routes required by the project instructions.

# 11. What `{order_id}` means

This is worth understanding.

The route:

```text
/orders/{order_id}
```

is a template.

For example:

```text
/orders/ORD-001
/orders/ORD-002
/orders/ORD-003
```

all match:

```text
/orders/{order_id}
```

API Gateway extracts:

```json
{
  "order_id": "ORD-001"
}
```

and gives that to Lambda as:

```python
event["pathParameters"]["order_id"]
```

Then `order_tracker.py` looks up that order.

The same happens with:

```text
/customers/{customer_id}
```

# 12. Lambda proxy integration

For every API method, we configured:

```text
AWS_PROXY
```

That means API Gateway automatically constructs an event containing things like:

```text
resource
httpMethod
pathParameters
```

and sends it to Lambda.

So:

```text
HTTP request

GET /orders/ORD-001
        ↓
API Gateway
        ↓
AWS_PROXY event
        ↓
{
    resource: "/orders/{order_id}",
    httpMethod: "GET",
    pathParameters: {
        order_id: "ORD-001"
    }
}
        ↓
order_tracker.lambda_handler()
```

This is exactly the event structure the supplied Lambda expects.

# 15. What remains for the entire project

There is still substantial work, but we're building it in layers so that each component is tested before being connected to the AI agent.

The remaining sequence is:

1. **Finish Order REST API** — deploy the API to a stage, obtain its public endpoint and directly test all three routes.

2. **AgentCore Gateway** — create `CustomerSupportGateway`, connect the Order REST API as an API target, connect `refund-processor` as the Lambda target, and verify both targets/tools. This is important because the rubric requires successful evidence from **two distinct Gateway-backed tools: one API-based and one Lambda-based**.

3. **AgentCore Memory** — create `CustomerSupportMemory` with semantic customer facts and customer-preference strategies. Eventually we'll prove that one session can store something such as “I am Jane; I prefer concise responses” and a different session for the same customer can recall it. The instructions specifically require those memory strategies and namespaces. 

4. **Knowledge Base / RAG** — upload `product_catalog.txt`, create the Bedrock Knowledge Base, configure embeddings/vector storage, sync it and test retrieval. We'll create this relatively late because the runbook identifies the OpenSearch Serverless-backed KB as the expensive resource. 

5. **Complete `main.py`** — this is the core coding phase. We still need to implement all TODOs: `BedrockAgentCoreApp`, configuration/clients, `get_namespaces`, `MemoryHook`, `search_knowledge_base`, `calculate_loyalty_discount`, Gateway MCP connection and the async `invoke()` entrypoint. Your starter currently contains these TODO sections.   

6. **Code Interpreter** — the loyalty tool will execute Python in AgentCore Code Interpreter to calculate points redemption, tier discount, final total, remaining points and points earned. It also needs the required fallback behavior.

7. **AgentCore Browser** — add `AgentCoreBrowser` to the Strands agent and prove it can access a live page.

8. **Deploy the complete AI agent** — configure and deploy `main.py` to AgentCore Runtime using the supplied AgentCore CLI workflow. The runbook recommends local build for this lab environment. 

9. **Run the six final rubric tests** — order tracking, refund, Knowledge Base/RAG, two-session memory, loyalty calculation, and live browser. These need **real deployed outputs**, not fabricated examples. The supplied instructions define the expected scenarios, including `ORD-001`, `ORD-002`, Platinum benefits, the two-session Jane memory test, the Gold/4250-point loyalty scenario and browser test. 

10. **Evidence + CloudWatch + reflection + submission** — capture test logs/screenshots, configure the requested CloudWatch evidence/alarm, write the 200–400 word reflection, audit `main.py` for remaining TODO/pass/placeholders, make sure no credentials are included, prepare the final ZIP, and then tear down costly AWS resources.
